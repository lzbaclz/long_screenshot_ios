日期：2026-09-15。**0.1.4（5）已开放内部 TestFlight，原组 Longlet Internal 已确认“正在测试 / 90 天后过期”。** 于 2026-09-15 00:49:19 Europe/London 手动上传成功。详细执行记录见 [Beta 5 开发与验收流程](../validation/beta-5-acceptance.md)。

## 用户现象与已确认原因

0.1.3（4）的真机反馈中，从最新聊天向更早内容滚动时，长图多段重复出现状态栏与导航栏。起始画面没有录屏胶囊，后续画面出现胶囊。消息在截图中看起来有序，但截图和总高度都不能证明正文没有缺失。

用完全程序生成的同色状态栏、导航栏和正文复现：向上匹配会交换两帧，使无胶囊的起始状态栏空白，与后续画面位移后的正文空白相似；胶囊又让同屏位置不同，旧判定把这种差异误当成移动证据。合成场景中，内部匹配区域从第 114 行开始，而导航栏实际到第 300 行。重放时固定栏占比小，去尾评分仍接受正确位移，于是多余固定像素随新增正文条带进入结果。

根因在首次自动匹配区域，不在 PNG 存储层。原始总高度即使保持 4556，混入的固定栏像素也会占据原本应由正文填充的行。不能把“高度没有变化”写成“没有丢行”。用户私人截图只用于结构观察，未复制进仓库或自动测试夹具。

## 修复方法与用户可见变化

1. 从上下边缘识别两帧同屏位置共享的横向结构，允许录屏胶囊、时钟变化和短距离空白间隔。整页候选的精确边界、移动证据与内部匹配范围都必须在固定结构带之外，避免从状态栏内部开始取新增正文。
2. 候选带有明确来源。采集层在重放前对整页候选再次复核；真实壁纸前景区域豁免，防止固定壁纸被误认作固定栏。负位移交换帧后再次识别出的前景也保留来源，不能仅靠 `preferredInsets == nil` 判断。
3. 输出仍使用原始像素，向上扩展替换完整顶部一次，向下扩展替换完整底部一次，边缘和新增正文同事务提交。修复不通过导出后擦除或重画固定像素解决重复栏，也没有放宽歧义阈值。
4. 捕捉详情新增已采用匹配区域、匹配方式、帧高与固定结构保护带，中英文均可查看，单位为原始图像像素。旧记录及未成功起拼显示“未记录”；壁纸前景和手动区域的保护带显示“不适用”，不将未知值显示成 0。后续失败候选不会覆盖最终采用值。

本轮受控输入的完整像素与真实模拟器手势验证已经确认：同色聊天页面上滑，顶部完整状态栏／导航栏保留一次，正文连续，底部保留原始输入栏。真实微信仍需新构建复测，不把模拟器结果视作所有真实布局通过。手动裁剪语义、每周免费导出额度和仅手动触发的 CI 保持现有约定。

## 验证边界

- 合成像素、模拟器真实手势与系统截图注入、iPhone 真机 ReplayKit 捕捉是不同证据。合成胶囊不会证明真机录屏指示的出现时机和系统回调顺序。
- 原生完整像素 oracle 用来证明受控输入的正文完整与原始固定栏保留；总高度、固定栏次数和核心位移一致不能单独证明这一点。
- 透明导航栏、结构不足、很大的首次滑动与缺乏真实重叠仍可能保守等待。原型的 800 像素首次位移歧义是既有边界，本轮不靠放宽阈值处理。
- 壁纸与气泡不是同一个平移平面，前景路径继续保留原始条带，壁纸本身可能存在接缝；不重画背景。
- Mac 和模拟器检查不能替代真机广播扩展的延迟、内存和温升测量。更新后仍需从用户原聊天入口复测，并结合新增详情数值判断。
